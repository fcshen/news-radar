## 1. 现在的运行形态

### 1.1 一条消息怎么走到你手机上

```
源头(RSS/新浪/金十/深交所/Telegram/行情)
   ↓ 每 30 秒抓一轮（config.yaml: runtime.poll_seconds）
radar/collectors.py  →  去重聚类（radar/dedupe.py）
   ↓
打分分级（radar/score.py：L0 忽略 / L1 入库 / L2 待看 / L3 紧急）
   ↓
分流：
   ├─ L2/L3 → 先摘要（radar/ai.py 智谱 glm-4-flash）→ 先入库 → 立刻推 Bark
   └─ 其余   → 排队摘要 → 入库，不推送
   ↓
radar/store.py 每轮重写 data/{events,feed,seen}.json
   ↓
workflow 后台每 2 分钟 git commit + push（tools/push_data.sh）
   ↓
前端每 30 秒轮询 data/feed.json，取最新一份（带秒级参数绕缓存）
   ↓
手机看板顶部「更新 HH:MM」= 数据生成时刻
```

### 1.2 为什么延迟是这个数（每一段的代价）

| 环节 | 现在 | 卡在哪，还能不能压 |
|---|---|---|
| 抓取间隔 | 30 秒 | 压到 20 秒只快 5 秒，但 33 个源被限流的风险明显上升，**故意不压** |
| AI 摘要 | 单条 ≤10 秒（超时 10s） | 智谱免费档并发只有 2，调高必 429，只能并行 2 条 |
| 推送 | 即时 | 已是最快，Bark 本身 1 秒内 |
| 数据入库→进仓库 | ≤2 分钟 | 再短会撞 Pages 构建限额（约 10 次/小时软限制） |
| 前端轮询 | 30 秒 | 再短手机耗电、且请求量翻倍 |

结论：通知这条线已经接近这条链的物理下限；看板那条线受 Pages 构建限制，2 分钟是性价比拐点。

### 1.3 四层保命机制（这是 11-27 那次停摆之后加的）

| 层 | 机制 | 触发条件 | 位置 |
|---|---|---|---|
| 1 | **续链**：每次运行**开局第一步**就把下一次派发进队列 | 总是 | `radar.yml` 第 78 行「续链·把下一次叫进队列」 |
| 2 | **兜底 cron** `*/20` | 续链断了 | `radar.yml` 第 14 行 |
| 3 | **watchdog** 独立工作流 `*/20` | 数据 `generated` ≥25 分钟 | `.github/workflows/watchdog.yml` |
| 4 | **外部巡检**（WorkBuddy automation，每小时） | 滞后 >10 分钟报异常，>30 分钟要求人工 | 会话外，非本仓库 |

关键前提：`concurrency.group: radar` + `cancel-in-progress: false`。GitHub 的语义是"同一组只允许 1 个在跑 + 1 个排队"，前一个结束 10 秒内排队那个自动接上。所以**只要单次运行时长（20 分钟）大于调度间隔，队列里就永远有接班人**，调度器迟到多久都不再致命。

### 1.4 看板顶部的时间会变色

`index.html:281 paintMeta()`：
- 灰 = 正常
- 黄（`.stale`）= 数据超过 20 分钟没更新
- 红（`.very-stale`）= 超过 60 分钟

这是给非技术用户看的状态灯，比查日志快。

### 阶段九 · 11-28 21:28 推送静默失败（第二次停摆）

定位过程：
1. 查 step 级状态 → 每步 success，排除卡死
2. 发现「提交首轮数据」只耗时 **1 秒** —— 真推送不可能这么快

## 5. 踩过的坑（按代价排序，后人别重踩）

| # | 坑 | 教训 |
|---|---|---|
| 1 | **`\|\| true` 吞掉 git 错误**，页面全绿、数据零条，停摆 20 分钟无人知 | 任何会失败的关键步骤，要么留可检测的标记，要么让 run 变红。**静默失败比报错可怕得多** |
| 2 | GitHub `schedule` 在公开仓库实测迟到 2~3 小时 | 不要靠"两次运行刚好接上"。必须让队列里常驻一个 pending（续链），或高频多次触发 |
| 3 | `GITHUB_TOKEN` 调 `workflow_dispatch` 回 204 却不创建运行 | 需要 `permissions: actions: write` **且** 显式传 `ref`。缺任一条就静默无效 |
| 4 | `raw.githubusercontent.com` CDN 锁 300 秒，`?t=` 穿不透 | 别拿它当主通道。Pages 带秒级参数反而能真回源 |
| 5 | Pages 边缘缓存 `max-age=600` | 读数据必须带**秒级**时间戳参数，分钟级不够 |
| 6 | 源给未来时间戳（`federalregister` 的文档公开日）霸占头部 | 过滤而不是钳制；钳制会被永久钉在顶部 |
| 7 | `concurrency.cancel-in-progress: true` + 外部高频触发 | 会掐死超时中的运行，形成"永远跑不完"。要排队就设 false |
| 8 | YAML `run: bash x.sh "data: $(...)"` 单行里含 `: ` | 被当成 mapping 报错。改 `run: \|` 块写法 |
| 9 | `healthcheck` 用 `>` 判阈值，测试时 `mins=0` 漏判 | 边界一律用 `>=` |
| 10 | 改前端忘升 `sw.js` 的 `SHELL` | 手机永远吃旧页面，改了等于没改。**当前 v17** |
| 11 | 智谱免费档并发只有 2 | 并发调高必 429，反而更多降级到模板 |
| 12 | 短快讯做 AI 摘要会丢信源与限定词 | <90 字中文快讯直接原文展示 |
| 13 | 鸿蒙不派发 `beforeinstallprompt`；纯血鸿蒙"添加至桌面"是书签壳 | 只能给手动路径引导，无法做成真 PWA |
| 14 | 开源 Bark 只支持苹果生态 | 纯血鸿蒙（5/6）装不上，需 Shark / Hotify（兼容 bark 协议），装完要改 `BARK_URL` |
| 15 | 本地测试用 8899 端口，被另一个项目占着，`http.server` 静默失败但 curl 返回 200 | 换端口 + 加 `--directory`；验证本地服务要同时看返回内容 |
| 16 | 页面不可见时 `requestAnimationFrame` 不执行，滚动无效 | 深链居中改用同步 `scrollIntoView` + 150ms 校正 |
