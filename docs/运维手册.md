## 一、改代码的完整流程

```bash
# 1. 开 VPN（国内直连 github.com 时通时断），代理端口 7897
cd /d/news-radar
export https_proxy=http://127.0.0.1:7897 http_proxy=http://127.0.0.1:7897 \
       HTTPS_PROXY=http://127.0.0.1:7897 HTTP_PROXY=http://127.0.0.1:7897

# 2. 先拉，避免与云端数据提交撞车
git pull --rebase --autostash

# 3. 改文件……（见下面"改什么动哪里"）

# 4. 语法自检（前端改了必做）
python -c "import re;h=open('index.html',encoding='utf-8').read();open('_c.js','w',encoding='utf-8').write('\n'.join(re.findall(r'<script>(.*?)</script>',h,re.S)))"
node --check _c.js && rm -f _c.js

# 5. 提交推送（tools/push.sh 已处理 rebase）
bash tools/push.sh "说明这次改了什么"
```

推送后 Actions 会自动起新运行，约 1~2 分钟生效。

**唯一例外**：`data/` 目录是云端单向写入，本地那份只是运行时副本，`tools/push.sh` 已排除，不要反向覆盖。

## 二、改什么动哪里

| 想改 | 文件 | 注意 |
|---|---|---|
| 增删消息源 | `config.yaml` → `sources` | 每源要有 `type` / `tier` / `enabled`；新源先用 `python tools/health.py` 验证可用 |
| 推送门槛（多少分才推） | `config.yaml` → `thresholds.push`（现 70） | 调低会明显增多通知 |
| 免打扰时段 | `config.yaml` → `notify.quiet_hours` | 现 23:30–07:00 |
| 看板样式/筛选/卡片 | `index.html` | **必须同时把 `sw.js` 的 `SHELL` 版本 +1** |
| 通知文案与深链 | `radar/notify.py` → `format_message()` / `board_link()` | 深链格式 `?e=<id>`，前端 `applyDeepLink()` 对接 |
| 摘要逻辑与提示词 | `main.py` → `_summarize_one()`；`radar/ai.py` → `summarize()` | 三级降级：智谱 → 硅基流动 → 本地模板 |
| 哪类消息跳过 AI | `main.py` → `SHORT_MSG_CHARS`（90） | 中文短快讯原文直出，摘要会丢信源 |
| 打分规则 | `radar/score.py` → `evaluate()`；词表 `radar/lexicon.py` | 改完用 `python tools/compare.py` 重放历史对比 |
| 采集器（新增源类型） | `radar/collectors.py` | 新函数要塞进 `collect()` 的分发 |
| 数据提交节奏 | `.github/workflows/radar.yml` 主循环里的 `sleep 120` | 别低于 120，会撞 Pages 构建限额 |
| 单次运行时长 | `radar.yml` 的 `inputs.minutes` 默认值（20）与 `config.yaml` 的 `max_run_minutes` | 必须 > cron 间隔，否则续链断档 |

## 三、日常检查（30 秒判断是否健康）

```bash
# 线上数据有多新
curl -s "https://fcshen.github.io/news-radar/data/feed.json?t=$(date +%s)" | python -c "
import json,datetime,sys
d=json.load(sys.stdin); g=datetime.datetime.fromisoformat(d['generated'])
n=datetime.datetime.now(g.tzinfo)
print('滞后', round((n-g).total_seconds()), '秒 | 共', d['total'], '条')
print('最新', d['events'][0]['ts'][11:19], d['events'][0]['source'])"
```

| 滞后 | 判断 |
|---|---|
| < 3 分钟 | 正常 |
| 3~25 分钟 | 可能正在交接或推送受阻，看一眼 Actions |
| > 25 分钟 | watchdog 应该已介入；若下轮还不动，按下面"停摆处置" |

不必每次都跑命令：**手机看板顶部「更新 HH:MM」变黄就是 20 分钟没更新，变红就是 1 小时。**

## 四、停摆处置（按顺序）

1. **先看是不是真的停了**
   ```bash
   curl -s "https://api.github.com/repos/fcshen/news-radar/actions/runs?per_page=5" \
     | python -c "import json,sys;[print(r['created_at'],r['name'],r['status'],r['conclusion'],r['event']) for r in json.load(sys.stdin)['workflow_runs']]"
   ```
   关注：是否还有 `radar` 处于 `in_progress` 或 `pending`。**两者都没有 = 续链断了。**

2. **看某个运行的每一步**
   ```bash
   curl -s "https://api.github.com/repos/fcshen/news-radar/actions/runs/<RUN_ID>/jobs" \
     | python -c "import json,sys;[print(s['number'],s['name'],s['conclusion']) for j in json.load(sys.stdin)['jobs'] for s in j['steps']]"
   ```
   公开仓库免认证。**重点看「提交首轮数据」和「推送失败则提醒手机」两步的耗时与结论**——如果 1 秒就 success，说明又是本地失败被吞。

3. **确认 workflow 没被 GitHub 自动禁用**
   打开 https://github.com/fcshen/news-radar/actions ，若顶部有 "This workflow was disabled" 需手动 Enable。Disable 状态下连 cron 都不会触发。

4. **手动拉起**
   仓库 Actions → 左侧 `radar` → `Run workflow` → 分支 main → minutes 留空（默认 20）→ Run。

5. **实在不行：本地跑一次把数据补上**（需要本机有 Python 与依赖）
   ```bash
   cd /d/news-radar && pip install -r requirements.txt && python main.py --minutes 8
   # 然后按"手动提交数据"推上去
   ```
   ⚠️ 本地跑会真的推 Bark 通知，深夜或不想被打扰时加 `--dry-run`。

## 五、手动提交数据（本地补数据后）

```bash
cd /d/news-radar
export https_proxy=http://127.0.0.1:7897 http_proxy=http://127.0.0.1:7897
bash tools/push_data.sh "data: 本地补抓 $(date -u +%Y-%m-%dT%H:%MZ)"
```

脚本行为：`fetch origin main` → `rebase origin/main` → 冲突则 `reset --hard origin/main`（data/ 可再生）→ 失败写标记并 exit 1。
**不要**再敲裸 `git pull` + `git add data/`：runner 与本地都可能没有 upstream，那正是 11-28 停摆的原因。

## 六、常见报错对照

| 现象 | 原因 | 处理 |
|---|---|---|
| `curl` 到 github.com 返回 `000` | VPN 没开或端口变了 | `netstat -ano \| findstr LISTENING \| findstr 789` 查端口；没开就开 VPN |
| `Updates were rejected` | 远端有数据提交 | `git pull --rebase --autostash` 后再推 |
| 推送后手机没变化 | `sw.js` 版本没升 | 升 `SHELL` 版本号，推送，手机刷新一次 |
| 手机点通知提示"已滚出最近 300 条" | 该条被新消息挤出 feed | 正常；深链会自动重拉一次，仍找不到才提示 |
| 看板时间一直不红但数据旧 | 手机本地缓存 | 下拉刷新；仍旧则清站点数据重开 |
| 通知全断但看板正常 | Bark 密钥失效或被限 | 仓库 Secrets 检查 `BARK_URL`；`python tools/alert.py "测试"` 可单测通道 |
| Actions 里一堆 `cancelled` | 排队位被新调度挤掉 | 正常现象，不是故障；`cancel-in-progress: false` 下只保留 1 个 pending |
| 单次运行只 1 秒就结束 | 极可能又踩"静默失败" | 按第四节第 2 步查 step 耗时 |

## 七、临时测试保命机制的注意点

改 `watchdog.yml` 或 `healthcheck.py` 的阈值做验证时：

- 用 `STALE_MIN=0` 覆盖即可，**不要直接改脚本里的默认值**（容易忘改回）
- 验证完检查一遍：`grep -n "STALE_MIN" .github/workflows/watchdog.yml` 应为 `${{ inputs.stale_min }}`，`main.py --minutes 8`
- 历史教训：曾把阈值和采集时长改成测试值后忘了恢复，堆了十几个测试提交

## 八、开关与停用

| 想做什么 | 做法 |
|---|---|
| 暂停采集（保留网站） | Actions → `radar` → `···` → Disable；同时 Disable `watchdog`，否则它会自动接管 |
| 完全停掉 | 同上 + 仓库 Settings → Pages 关掉；网站下线但代码保留 |
| 只停通知、继续采集 | `config.yaml` → `notify.bark.enabled: false` |
| 临时提高/降低通知量 | `thresholds.push`：70 → 80 更少，→ 60 更多 |

**注意**：只 Disable `radar` 不 Disable `watchdog` 的话，watchdog 每 20 分钟会检测到停摆并自己跑 8 分钟采集——这是设计如此。
